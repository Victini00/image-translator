# image-translator

**만화를 일본어에서 한국어로 번역하는 프로젝트입니다.**

| 원본 | 번역 결과 | 수정 결과 |
|---|---|---|
| ![원본](docs/demo_before.webp) | ![결과](docs/demo_after.png) | ![결과](docs/demo_after_v2.png) | 

원본 이미지에서 글자를 찾아 읽고, 번역하고, 원본 글자를 지운 자리에 번역문을 자연스럽게 그려 넣습니다.
결과를 브라우저에서 직접 고칠 수 있는 편집 도구도 함께 제공합니다.

API 호출을 사용하는 파이프라인의 경우, 다른 언어에서의 번역도 가능합니다. 

> 개인 학습용 프로젝트입니다. 번역 대상 이미지의 저작권은 사용자 본인이 확인해야 합니다.

## How It Works

<!-- TODO: 파이프라인 다이어그램 -->

파이프라인은 네 단계로 구성됩니다.

| 단계 | 하는 일 | 사용 모델 |
|---|---|---|
| **Masking** | 글자 영역 검출 + 말풍선 검출 → 문단 단위로 묶기 | PP-OCRv5 detection, YOLOv8 말풍선 검출기 |
| **Recognition / Translation** | 일본어 원문을 읽고 한국어로 번역 | PP-OCRv5 파인튜닝 + hell0ks LoRA, **또는** Gemini API |
| **Cleaning** | 원본 글자 지우기 | LaMa (말풍선 밖), 단색 채우기 (말풍선 안) |
| **Rendering** | 번역문을 박스에 맞춰 자동 줄바꿈·크기 조절해 그리기 | Pillow |

### 두 가지 실행 경로

읽고 번역하는 부분만 다른 두 가지 경로가 있습니다.

**`image_translator_v1.py` (로컬 전용)** — PaddleOCR로 읽고 hell0ks 7B + LoRA로 번역합니다. 외부 API가 필요 없지만 GPU가 필요합니다.

**`image_translator_v1_using_gemini.py` (하이브리드, 권장)** — 글자 **위치 검출**은 로컬 모델을 그대로 쓰고, **읽기와 번역**만 Gemini API에 맡깁니다. 위치는 로컬 모델이 픽셀 단위로 정확한 반면 글자 인식 품질은 API 쪽이 확실히 낫기 때문입니다. 실제 개선 사례는 [Design Decisions](#5-하이브리드-구조-위치는-로컬-읽기는-api)에 정리했습니다.

## Getting Started

### 1. 저장소와 외부 프로젝트

```bash
git clone https://github.com/Victini00/image-translator.git
cd image-translator

git clone https://github.com/PaddlePaddle/PaddleOCR.git external/PaddleOCR
```

### 2. 파이썬 환경

Python 3.10 기준입니다.

```bash
conda create -n image-translator python=3.10
conda activate image-translator
pip install -r requirements.txt
```

`requirements.txt`의 아래 3개는 일반 PyPI 패키지가 아니라 별도 설치가 필요합니다(파일 상단 주석 참고).

- `torch` / `torchvision` — CUDA 빌드(`+cu128`)
- `paddleocr` — GitHub 특정 커밋에서 직접 설치
- `paddlepaddle-gpu` — PaddlePaddle 개발 빌드 wheel

### 3. API 키 (Gemini 경로를 쓸 경우)

프로젝트 루트에 `.env` 파일을 만들고 한 줄 넣습니다. 키는 [Google AI Studio](https://aistudio.google.com)에서 카드 등록 없이 발급받을 수 있습니다.

```
GEMINI_API_KEY=발급받은_키
```

`.env`는 `.gitignore`에 걸려 있어 저장소에 올라가지 않습니다.

### 4. 모델 준비

| 모델 | 위치 | 받는 방법 |
|---|---|---|
| 일본어 인식 파인튜닝 (v4) | `models/ocr/PP-OCRv5_..._v4/complete_model/` | **저장소에 포함** (약 17MB) |
| PP-OCRv5 detection | `~/.paddlex/official_models/` | 첫 실행 시 자동 |
| 말풍선 검출 (YOLOv8) | HuggingFace 캐시 | 첫 실행 시 자동 |
| LaMa 인페인팅 | `models/inpainting/LaMa/big-lama.pt` | 첫 실행 시 자동 (약 196MB) |
| hell0ks 번역 모델 | HuggingFace 캐시 | 첫 실행 시 자동 (7B) |
| hell0ks LoRA (직접 학습) | `models/translation/.../lora/v1/` | 저장소 미포함 |

`models/` 하위 폴더에 각각 안내 README가 있습니다. 학습 체크포인트 등 무거운 파일은 저장소에서 제외했지만, 폴더 구조는 코드가 기대하는 경로 그대로 유지되어 있습니다.

### 5. 실행

필수 인자는 이미지 경로 하나뿐입니다.

```bash
cd src

# 하이브리드 (권장)
python image_translator_v1_using_gemini.py --img ../data/raw/images/test2.png

# 로컬 전용
python image_translator_v1.py --img ../data/raw/images/test2.png
```

결과는 `output/pipeline_v1_gemini/` (또는 `output/pipeline_v1/`)에 저장됩니다.

| 파일 | 내용 |
|---|---|
| `{이름}_paragraphs.json` | 문단별 좌표·원문·번역문 |
| `{이름}_cleaned.png` | 원본 글자를 지운 이미지 |
| `{이름}_rendered.png` | **최종 결과** |

자주 쓰는 옵션:

```bash
--rec-score-thresh 0.5      # 인식 신뢰도 임계값 (기본 0.4)
--bubble-conf 0.4           # 말풍선 검출 임계값 (기본 0.5)
--max-font-size 40          # 글자 최대 크기 (기본 36)
--gemini-model gemini-3.6-flash
```

각 단계를 따로 실행할 수도 있습니다(`src/models/` 안의 스크립트). 모든 스크립트가 `--help`를 지원합니다.

## Design Decisions

만들면서 내린 판단들과 그 근거를 정리했습니다.

### 1. 문단은 말풍선을 기준으로 묶는다

OCR은 글자를 **줄 단위**로 검출합니다. 하지만 번역은 줄 단위로 하면 안 됩니다. 말풍선 안의 세 줄은 이어진 한 문장이고, 따로 번역하면 문맥이 끊깁니다.

그래서 별도의 **말풍선 검출 모델(YOLOv8)**을 함께 돌리고, 각 OCR 줄의 **중심점이 어느 말풍선 안에 있는지**로 묶습니다. 어느 말풍선에도 속하지 않는 줄(효과음, 작가 크레딧 등)은 각각 독립 문단이 됩니다.

이 구조 덕분에 말풍선 안/밖을 구분할 수 있게 되었고, 그 구분이 이후 **지우는 방식**과 **글꼴 선택**까지 결정합니다.

### 2. 문서 회전 보정 좌표계를 맞춘다

PaddleOCR은 문서 방향 분류(`use_doc_orientation_classify`)를 켜면 이미지를 **내부적으로 회전시켜** 처리합니다. 그래서 OCR 결과 좌표는 원본 이미지 좌표가 아니라 회전된 좌표계에 있습니다.

문제는 말풍선 검출(YOLO)은 원본 이미지를 그대로 보기 때문에 **두 좌표계가 서로 다르다**는 점입니다. 처음에는 회전각을 90도로 고정했다가, 이미지마다 값이 다르다는 것을 확인했습니다(실측: shirobako 90도, 다른 이미지 270도).

결국 세 단계로 정리했습니다.

1. OCR을 먼저 돌려 **실제 적용된 회전각**을 읽어낸다
2. 그 각도로 말풍선 좌표를 OCR 좌표계로 변환해 그룹핑한다
3. 저장 직전에 모든 좌표를 **원본 이미지 좌표계로 되돌린다**

3번이 없으면 이후 Cleaning 단계가 원본 이미지의 엉뚱한 영역을 지웁니다.

### 3. 마스킹은 말풍선이 아니라 글자 줄 폴리곤 기준으로

처음에는 말풍선 전체(`bubble_bbox`)를 지웠는데, LaMa가 **말풍선 테두리와 흰 배경까지 주변 그림으로 메워버렸습니다.** 그러면 렌더링 때 말풍선을 통째로 다시 그려야 합니다.

그래서 마스크를 **글자 줄 폴리곤 + 여유 픽셀**로 바꿨습니다. 말풍선은 그대로 두고 글자만 지우므로 원본의 말풍선 모양이 보존됩니다. `bubble_bbox`는 지우는 용도가 아니라, 텍스트를 배치할 위치를 정하는 참고용으로만 씁니다.

### 4. 지우는 방식을 말풍선 안/밖으로 나눈다

| 위치 | 방식 | 이유 |
|---|---|---|
| 말풍선 **안** | 주변 색으로 단색 채우기 | 배경이 균일한 단색이라 인페인팅이 불필요하고, 오히려 얼룩이 생길 수 있음 |
| 말풍선 **밖** | LaMa 인페인팅 | 배경에 그림이 있어서 복원이 필요함 |

팽창(dilate) 픽셀도 다르게 잡았습니다. 단색 채우기는 1px면 충분하지만, LaMa는 글자 흔적이 남지 않도록 4px로 넉넉히 잡고 주변 30px을 문맥으로 함께 넘깁니다.

### 5. 하이브리드 구조: 위치는 로컬, 읽기는 API

`recognition`(글자 읽기) 품질이 계속 발목을 잡았습니다. 파인튜닝(v4)까지 했는데도 특정 패턴에서 반복적으로 틀렸습니다.

여기서 **전부 API로 넘기지 않고 위치 검출만 로컬에 남긴** 이유는, 위치 정밀도가 이후 단계 전체를 좌우하기 때문입니다. API 모델에 이미지를 통째로 주고 좌표까지 받으면 대략적인 위치만 나오는데, 그러면 마스크가 부정확해져 글자가 덜 지워지거나 배경이 과하게 지워집니다. **로컬 모델이 확실히 잘하는 것(픽셀 단위 위치)은 남기고, 확실히 못하는 것(글자 읽기)만 교체**하는 구성입니다.

결과적으로 로컬 인식이 반복적으로 틀리던 사례들이 해결되었습니다.

| 실제 원문 | 로컬 (PaddleOCR) | Gemini |
|---|---|---|
| `アニメーター` (애니메이터) | `ア二xIタI` | `アニメーター` |
| `おい望月〜` | `おい望月り` | `おい望月〜` |
| `ごめ〜ん` | `ごめりん` | `ごめ〜ん` |
| `今日という` | `介日という` | `今日という` |
| `女の子が上に乗っかってるん` | `数の子が上に素っかってるん` | `女の子が上に乗っかってるん` |

### 6. API 호출은 이미지 한 장당 한 번

처음에는 문단마다 API를 호출했습니다. 문단이 20개면 요청 20건입니다. 무료 티어의 **일일 요청 한도(RPD)**가 몇 장 테스트하자마자 소진되었습니다.

두 단계로 줄였습니다.

1. 문단별 crop 이미지를 **한 요청에 모두 담아** 한 번에 처리 (각 이미지 앞에 `문단 id=N` 라벨을 붙여 순서·식별 보장)
2. 인식과 번역을 **하나의 응답 스키마**로 합쳐 한 번 더 절반으로 (`{id, 원문, 번역문}`)

최종적으로 **이미지 한 장 = 요청 1건**, 문단 수와 무관합니다. 부수적으로 실행 시간도 줄었습니다(shirobako 기준 95초 → 45초).

### 7. 실패는 문단 단위로 격리한다

API는 실패할 수 있습니다. 전체가 실패하면 전부 로컬 모델로 폴백하고, **특정 문단만 응답에서 빠지면 그 문단만** 폴백합니다.

인식은 성공했는데 번역만 실패한 경우에는 **더 정확해진 원문(`gemini_text`)을 남겨둡니다.** 그러면 로컬 번역 모델이 그 원문을 받아 번역하므로, API가 부분적으로만 동작해도 결과가 개선됩니다.

또한 재시도 정책을 오류 종류별로 나눴습니다.

| 응답 | 처리 |
|---|---|
| 429 (요청 한도) | 응답이 알려주는 권장 대기 시간만큼 기다린 뒤 재시도 |
| 500/502/503/504 (서버 일시 오류) | 지수 백오프(3 → 6 → 12초) 후 재시도 |
| 그 외 | 즉시 폴백 |

503은 무료 티어에서 생각보다 자주 발생합니다. 처음에는 429만 재시도해서 503이 뜨면 그대로 로컬 폴백으로 넘어갔는데, 재시도를 추가하자 **한 번 만에 9개 문단 전부 성공**했습니다. "한도가 빨리 닳는다"고 느꼈던 상황의 상당수가 실제로는 일시적 서버 혼잡이었습니다.

### 8. 글자 배치: 줄을 더 쓴 만큼 글자가 커질 때만 줄을 늘린다

번역문은 원문보다 길어지거나 짧아집니다. 정해진 박스 안에 맞추는 규칙을 우선순위로 정리했습니다.

1. **박스를 넘지 않는다** — 절대 조건. 말풍선 밖으로 글자가 삐져나오면 결과물로서 실패입니다.
2. **단어(어절)를 자르지 않는다** — 조사가 잘려 다음 줄로 넘어가면 읽기 나쁩니다. 줄바꿈은 띄어쓰기 기준으로만 합니다.
3. **박스 공간을 잘 쓴다** — 글자는 클수록 좋지만, 그러자고 줄을 무의미하게 쪼개지는 않습니다.

3번이 처음부터 이렇지는 않았습니다. 원래는 **줄 수를 1순위로 최소화**하고 같은 줄 수 안에서만 글자를 키웠습니다. "원문이 한 줄이던 짧은 대사를 굳이 두 줄로 쪼개지 말자"는 의도였는데, 이 규칙이 **박스 크기를 전혀 보지 않는다**는 문제가 있었습니다.

실제로 133×160 박스에서 이런 일이 벌어졌습니다.

| 후보 | 세로 점유 | 판정 |
|---|---|---|
| 21px, 3줄 | 51% | 박스에 들어가는데도 **버려짐** |
| 14px, 2줄 | 22% | 선택됨 |

글자를 33% 깎아서 얻은 것이 "한 줄 덜 쓰기"뿐이고, 말풍선이 클수록 손해가 커지는 구조였습니다.

그래서 판정 기준을 바꿨습니다. 줄 수가 적은 쪽에서 시작해, **줄을 하나 더 쓰는 대신 글자가 일정 비율(현재 15%) 이상 커지는 경우에만** 그쪽으로 갈아탑니다. 줄만 늘고 글자는 별로 안 커지는 조합은 여전히 걸러지므로 원래 의도도 유지됩니다.

여기서 2번(띄어쓰기 기준 줄바꿈)이 안전장치 역할을 합니다. `영차` 처럼 **공백이 없는 짧은 대사는 애초에 한 줄로만 나오므로**, 글자를 키우는 방향으로 바꿔도 잘게 쪼개질 수 없습니다.

실제 문단 50개로 측정한 변화입니다.

| | 이전 | 이후 |
|---|---|---|
| 평균 글자 크기 | 16.6px | **21.0px** |
| 평균 세로 점유 | 47% | **69%** |
| 평균 줄 수 | 2.24 | 2.88 |

구현은 2단계입니다. 최대~최소 크기 범위를 **전부 훑어서** 박스에 들어가는 조합을 모은 뒤 위 기준으로 고릅니다. 위에서부터 내려오며 처음 맞는 것을 고르지 않는 이유는, 후보 전체를 봐야 "줄을 늘렸을 때 얼마나 커지는지"를 비교할 수 있기 때문입니다.

최소 크기까지 줄여도 안 들어가면(단어 하나가 박스보다 긴 경우 등) 그때만 글자 단위로 쪼개고, 1px까지 줄여서라도 **반드시 박스 안에 넣습니다.** 우선순위 1번이 2번보다 위이기 때문입니다.

### 9. 편집 미리보기를 최종 결과와 일치시키기

웹 편집기에서 "지금 보이는 것"과 "저장했을 때 나오는 것"이 다르면 편집 도구로서 의미가 없습니다. 이걸 맞추는 데 세 번의 시도가 필요했습니다.

**1차: HTML/CSS로 그리기** — 실패. 세 가지가 어긋났습니다.
- 말풍선 밖 텍스트의 **흰 테두리(stroke)를 아예 그리지 않았음**
- PIL은 글자 **윗선** 기준으로 찍는데 CSS는 `line-height` 여백을 위아래로 나눠 배분 → 세로 위치가 밀림
- 가로 중앙 정렬의 기준 폭이 서로 달랐음

**2차: 조판 알고리즘을 JS로 이식** — 줄바꿈은 일치했지만 **글자 크기가 1px씩 어긋났습니다.** 원인은 폭 측정 방식이었습니다. PIL은 FreeType 힌팅이 적용된 잉크 경계를 재고, 브라우저 canvas는 서브픽셀로 잽니다. 측정 기준을 `advance width`에서 `잉크 경계`로 바꿔 좁혔지만 약 3% 차이가 남았고, 이건 래스터라이저가 다른 이상 재구현으로는 없앨 수 없습니다.

**3차: 서버가 계산하고 브라우저는 그리기만** — 해결. 폰트 크기, 줄바꿈, **각 줄의 좌표까지** 서버가 실제 렌더링과 **똑같은 함수**로 계산해 내려주고, 브라우저는 그 좌표대로 canvas에 그립니다. 같은 함수를 쓰므로 정의상 일치합니다.

검증은 미리보기 합성 이미지와 실제 결과 PNG를 **픽셀 단위로 비교**했습니다.

| 항목 | 결과 |
|---|---|
| 세로 오프셋 | **0px** (완전 일치) |
| 가로 오프셋 | 1px 이내 |
| 단일 행 문단 차이 | 5픽셀 |
| 남은 차이 | 글자 가장자리 안티에일리어싱 (래스터라이저 차이, 제거 불가) |

### 10. 공유 로직을 의존성 없는 모듈로 분리

9번을 구현하려면 웹 서버가 렌더링 모듈의 배치 함수를 써야 하는데, 그 모듈은 상단에서 `torch`/`transformers`를 import합니다. 결과적으로 **웹 서버 기동에 8초**가 걸리고, 환경에 따라 numpy/numba 충돌로 아예 실패했습니다.

배치 규칙과 폰트 경로만 `render_layout.py`로 분리하고 양쪽이 이걸 import하도록 바꿨습니다(의존성은 Pillow만). **기동 시간 8초 → 0.11초**가 되었고, 규칙이 한 곳에만 있으므로 미리보기와 결과가 갈라질 여지도 없어졌습니다.

### 11. 사용자 편집은 자동 규칙보다 우선한다

편집 결과를 저장할 때, JSON에 선택적 필드를 추가해 렌더링 단계가 자동 계산 대신 그 값을 쓰도록 했습니다.

| 필드 | 효과 |
|---|---|
| `render_bbox` | 말풍선 기준 자동 위치 대신 사용자가 옮긴 위치 사용 |
| `font_size` | 자동 크기 조절을 건너뛰고 지정한 크기 사용 |
| `translated_text`의 `\n` | 자동 줄바꿈보다 우선하는 강제 개행 |

필드가 없으면 기존 동작 그대로이므로, 편집 기능을 안 쓰는 CLI 실행에는 영향이 없습니다. 재렌더링 시에는 번역을 다시 하지 않아 몇 초 만에 끝납니다.

### 12. 브라우저가 거부하는 폰트 복구

미리보기를 실제 폰트로 그리려면 폰트 파일을 브라우저에 넘겨야 하는데, 효과음용 글꼴(HY피오피M)이 **크롬에서 로드 거부**되었습니다. `cmap` 테이블이 실제 글리프 수를 넘는 인덱스를 가리키고 있었습니다. PIL은 관대해서 그냥 읽지만 브라우저는 OTS 검증에서 막습니다.

fontTools로 **유효한 글리프를 가리키는 매핑만 남겨 cmap을 재구성**해서 전달하도록 했습니다(결과는 메모리에 캐시). 원본 파일은 건드리지 않으므로 실제 렌더링에는 영향이 없습니다.

## Model Selection & Tuning

감이 아니라 측정해서 정한 값들입니다.

### Detection 모델: server vs mobile

두 이미지로 실측 비교한 결과 **`PP-OCRv5_server_det`**를 기본값으로 채택했습니다. 검출 누락이 더 적었습니다.

다만 절대 우위는 아니었습니다. **아주 작은 반복 의성어**(パチパチ 류)는 mobile이 더 잘 잡는 경우가 있었습니다. 트레이드오프를 알고 고른 것이라 코드 주석에도 남겨두었습니다.

### 인식 신뢰도 임계값: 0.4

배경 패턴이나 장식을 글자로 오인식하는 노이즈를 걸러내야 했습니다. 값을 감으로 정하지 않기 위해, 검출된 모든 줄의 신뢰도를 덤프해서 분포를 봤습니다.

| 구분 | 값 |
|---|---|
| 노이즈(오인식)의 **최고** 신뢰도 | 0.28 |
| 실제 텍스트의 **최저** 신뢰도 | 0.544 |

두 값 사이에 뚜렷한 간격이 있어서 그 사이인 **0.4**로 정했습니다. 이러면 실제 텍스트를 하나도 잃지 않으면서 노이즈만 걸러집니다.

구현에서도 한 번 막혔습니다. PaddleOCR 생성자의 `text_rec_score_thresh` 옵션을 쓰면 `rec_texts`/`rec_scores`만 필터링되고 `dt_polys`는 그대로 남아 **세 배열의 길이가 어긋나 IndexError**가 납니다. 그래서 옵션을 쓰지 않고, 결과를 받은 뒤 세 배열을 함께 묶어 필터링하는 방식으로 처리했습니다.

### 인식 모델 파인튜닝 (v4)

PP-OCRv5 mobile recognition 모델을 일본어 만화 텍스트로 파인튜닝했습니다.

| 항목 | 값 |
|---|---|
| 베이스 | `PP-OCRv5_mobile_rec` |
| 학습률 | `1.0e-05` (파인튜닝이라 낮게) |
| 에폭 | 30 |
| 문자셋 | 직접 구성한 일본어 사전 |
| 학습 데이터 | TRDG로 생성한 합성 이미지 (JParaCrawl 코퍼스 기반) |

학습 설정은 `config/PP-OCRv5_mobile_rec.yml`에 있고, 파일 상단 주석에 실행 방법과 v4에서 바꾼 값이 정리되어 있습니다.

파인튜닝으로 전반적인 정확도는 올랐지만 **세로쓰기 특수문자 문제는 해결되지 않았습니다.** 원인은 학습 데이터에 있었습니다 ([What Didn't Work](#2-세로쓰기-학습-데이터-생성) 참고).

### 글꼴 선택

말풍선 안쪽 글꼴을 후보 4종으로 좁힌 뒤, **실제 파이프라인을 돌려 완성된 결과물 4장을 만들어 비교**했습니다. 글꼴 견본만 봐서는 실제 만화 위에 얹었을 때의 느낌을 알 수 없기 때문입니다.

| 위치 | 채택 | 이유 |
|---|---|---|
| 말풍선 안 | Gmarket Sans Medium | 본문 가독성 |
| 말풍선 밖 (효과음) | HY피오피M + 흰 테두리 | 그림 위에 얹혀도 읽히도록 |

## What Didn't Work

시도했지만 실패했거나 폐기한 것들입니다.

### 1. OCR 오류 교정 단계

인식 결과를 번역 전에 **한 번 교정**하는 단계를 넣으려 했습니다. 인식 모델을 다시 학습하는 것보다 비용이 적을 것 같았기 때문입니다. 두 모델을 시도했고 둘 다 실패했습니다.

**hell0ks (번역에 쓰는 모델 그대로)** — 교정 지시를 이해하지 못했습니다. 프롬프트를 그대로 되뱉거나, 같은 말을 반복하거나, 교정 대신 번역을 해버렸습니다. 반복 억제 파라미터(`repetition_penalty`, `no_repeat_ngram_size`)를 조정해도 근본적인 지시 따르기 실패는 그대로였습니다. 번역에 특화된 모델이라 다른 작업 지시를 소화하지 못한 것으로 보입니다.

**Qwen2.5-7B-Instruct** — 지시는 따랐지만 **중국어 간체가 섞여 나왔습니다**(`员`, `绪`, `确`, `观`, `虑` 등). 일본어 한자를 중국어 간체로 "교정"해버린 것입니다. 프롬프트를 강화하고, 간체 문자 목록을 만들어 의심스러운 교정을 되돌리는 방어 코드까지 넣었지만, 다음 실행에서 **목록에 없던 새로운 간체가 나타났습니다.** 목록 방식으로는 끝이 없다고 판단해 폐기했습니다.

교정 단계는 파이프라인에 넣지 않았습니다. 코드는 `src/models/translation_correction.py`에 실패 기록과 함께 참고용으로 남겨두었습니다. **결과적으로 이 문제는 다른 방향에서 풀렸습니다** — 교정 단계를 추가하는 대신, 인식 자체를 더 잘하는 모델로 교체하는 하이브리드 구조로 우회했습니다.

### 2. 세로쓰기 학습 데이터 생성

`ー`(장음)를 `I`나 `ツ`로, `〜`를 다른 글자로 오독하는 패턴이 반복적으로 관찰되었습니다. 학습 데이터를 확인해보니 **세로쓰기용으로 생성했다는 이미지가 가로쓰기 이미지와 시각적으로 동일했습니다.** 데이터 생성기(TRDG)의 방향 옵션(`-or 1`)이 실제로 적용되지 않은 것으로 보입니다.

더 정확한 원인은 그 다음에 드러났습니다. 진짜 문제는 이미지 전체의 방향이 아니라, **세로 조판에서 `ー`나 `〜` 같은 방향에 민감한 문자가 90도 회전되어 조판된다**는 점이었습니다. 학습 데이터에는 그런 회전된 형태가 전혀 없었으므로, 모델이 회전된 장음을 처음 보는 글자로 취급하는 것은 당연한 결과였습니다.

이 수정은 아직 하지 않았습니다. 하이브리드 경로에서는 발생하지 않는 문제라 우선순위가 내려갔고, 재학습 계획에 남겨두었습니다.

### 3. Claude API 경로

원래 하이브리드는 Claude API로 먼저 구현했습니다. 코드는 완성했지만 API 크레딧이 없어 실제 호출을 못 했고, 무료 티어가 있는 Gemini로 전환했습니다. 구조(문단 crop → 배치 요청 → id 매칭 → 폴백)는 그대로 옮겼습니다.

### 4. 웹 UI 진행률이 한 번에 몰려 표시되던 문제

단계별 진행률을 오케스트레이터의 출력에서 읽는 방식으로 만들었는데, 처음에는 `0/4`에서 갑자기 `4/4`로 건너뛰었습니다. 자식 프로세스의 stdout이 **버퍼링**되어 단계 표시가 끝에 몰아서 도착했기 때문입니다. `PYTHONUNBUFFERED=1`을 주어 해결했습니다.

## Limitations & Roadmap

### 현재 한계

- **세로쓰기 특수문자 오독** — 로컬 인식 모델의 문제입니다. Gemini 경로에서는 발생하지 않습니다.
- **검출 누락** — 특이한 글꼴, 획이 적은 글자, 후리가나가 조밀한 영역은 검출 단계에서 놓칠 수 있습니다. 웹 편집기의 덧칠 기능으로 보정할 수 있습니다.
- **Gemini 무료 티어 한도** — 공개 서비스로 쓰기에는 일일 요청 한도가 부족합니다.
- **웹 UI는 1인용 로컬 도구 전제** — 개발 서버, 메모리 기반 작업 상태, 단일 API 키 등 다중 사용자를 고려하지 않았습니다.
- **글꼴 라이선스** — 웹 편집기는 미리보기를 위해 글꼴 파일을 브라우저로 전송합니다. 공개 서비스로 배포한다면 재배포 라이선스 확인이 필요합니다.

### 계획

- **인식 모델 재학습** — 두 종류의 데이터셋을 추가할 계획입니다.
  - 실제 만화 스타일의 글꼴과 배치를 반영한 데이터셋 (현재 학습셋은 기본 글꼴 + 흰 배경이라 도메인 차이가 큼)
  - 세로 조판에서 회전되는 특수문자가 반영된 데이터셋
- **웹 서비스화 검토** — 다중 사용자 대응, 글꼴 교체, 배포 환경 구성
